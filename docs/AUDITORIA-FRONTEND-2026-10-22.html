1

Job manifest vai falhar: a rota de assets não existe no Forgejo

CONFIRMADO (sem token)scripts/publish-release.mjs · collectAssets()

collectAssets() chama GET /repos/{owner}/{repo}/releases/assets/{id} para ler cada .sig. Teste empírico contra v16.next.forgejo.org (Forgejo 16.0.6 / gitea 1.22): a rota responde 404 page not found — 404 do router Go, não o 404 JSON da API (comparado lado a lado com /releases/{id}, que devolve {"message": ...}). O mesmo .sig via browser_download_url responde 200 com o conteúdo de texto da assinatura, anônimo.

Efeito no próximo release: fail('GET asset ... -> 404') aborta o job manifest → updater/latest.json nunca é regenerado no main → o in-app updater (que aponta para esse arquivo) anuncia 1.1.7 para sempre. Os artefatos são publicados (jobs publish ok), só o manifesto morre.

Melhor fix: baixar o .sig direto de asset.browser_download_url (que o próprio JSON do release já traz). Funciona anônimo no Forgejo, funciona no GitHub para repo público, e elimina a dependência da rota de API. A autorização só é necessária para o upload, que continua como está.
Esforço: ~15 min, ajuste pontual no loop de collectAssets + rodar os testes existentes de updater-manifest.
manter a rota de API e confiar que o TOKEN do CI resolve. Não foi possível testar com token; e o 404 é do router (rota ausente), o que token nenhum resolve. Deixa o próximo release como aposta.
2

Quem tem a 1.1.7 instalada nunca verá a 1.1.8 — e o modal vai contradizer o updater

CONFIRMADOtauri.conf.json (tag v1.1.7 vs main) · src-tauri/src/commands.rs

O binário 1.1.7 compilado embute https://github.com/Umbr-Corp/OpenScrcpy/releases/latest/download/latest.json. Esse arquivo ainda existe no GitHub e diz "version": "1.1.7" — não vai mudar, porque releases novas só entram no Forgejo. Pior: o check_app_update (Rust) já aponta para o Forgejo, então quando a 1.1.8 sair, o modal anuncia atualização disponível (Forgejo diz 1.1.8) e, ao clicar em "Baixar e instalar", o plugin updater diz "você está na última versão" (GitHub diz 1.1.7). Dois endpoints, duas verdades, na mesma tela.

Melhor fix (ponte de um arquivo): subir um latest.json novo no release v1.1.7 do GitHub com as URLs de download apontando para o Forgejo. A assinatura do updater é sobre os bytes do artefato, independente do host — então o manifesto pode morar no GitHub e baixar do Forgejo. Usuário da 1.1.7 vê 1.1.8, baixa, assinatura confere, reinicia; a partir da 1.1.8 o endpoint é o Forgejo e a corrente fecha.
Esforço: ~20 min manuais hoje (regenerar o manifesto com URLs do Forgejo, deletar+re-upload do asset latest.json na release v1.1.7 do GitHub) + ~10 min de decisão sobre se vira processo documentado.
espelhar releases inteiras nos dois hosts para sempre — infra duplicada e permanente para resolver um problema de uma fronteira de migração.

4

bump_version.yml não atualiza nem commita o Cargo.lock

CONFIRMADO.github/workflows/bump_version.yml:55-62

O workflow faz npm version (package.json + package-lock.json), jq (tauri.conf.json) e sed (Cargo.toml) — e o git add lista esses quatro arquivos. O Cargo.lock fica com a versão antiga; cada build de dev re-escreve o lock e deixa a working tree suja, e o PR de bump sai desatualizado. O bump manual da 1.1.7 (PR #21) incluiu o lock; o automatizado não.

Melhor fix: após o sed no Cargo.toml, rodar cargo update -p openscrcpy --precise não existe para versão própria — na prática: tocar a versão no Cargo.lock com sed também (a linha name = "openscrcpy"/version), e adicionar src-tauri/Cargo.lock ao git add.
Esforço: ~10 min, duas linhas no workflow.
5

tag_on_merge.yml faz git tag -f + push --force sobre tags publicadas

CONFIRMADO — RISCO OPERACIONAL.github/workflows/tag_on_merge.yml:38-39

O job só dispara para branches chore/version-bump-v*, mas re-executar o workflow (retry manual do Actions, ou reabertura de PR antiga) sobrescreve a tag de uma release já publicada e re-dispara o build de release sobre assets existentes. O uploadAsset até apaga e re-upa assets homônimos, então o resultado é coerente — mas uma tag assinada não pode ser movida sem invalidar o release, e nada impede isso hoje.

Melhor fix: antes de criar, checar git rev-parse -q --verify refs/tags/v$VERSION e abortar com mensagem clara se a tag já existe. Remove a força do -f/--force do caminho normal.
Esforço: ~10 min, um step condicional.
remover o --force sem checagem — aí o retry legítimo (tag criada mas push falhou) passa a falhar em vez de sobrescrever. A checagem cobre os dois casos.
