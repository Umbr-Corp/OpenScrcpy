P1 · Confirmados

Cada card traz a prova, o melhor fix discutido e uma alternativa descartada.

1

showAlert por chunk no auto-update

CONFIRMADOApp.tsx:206-216

Cada evento Progress do plugin updater chama showAlert, que faz setAlertState com objeto novo a cada chamada → re-render do App inteiro (Sidebar de ~600 linhas, ControlPanel, LogPanel). Números: 13 call sites de showAlert confirmados por grep; com AppImage de ~100 MB, são centenas de eventos de download. O custo é por evento, não por percentual visível.

Melhor fix: guardar o último percentual inteiro exibido (lastPctRef) e só chamar showAlert quando Math.round(p) muda — cai de centenas para ~100 re-renders, distribuídos pela duração do download.
Esforço: ~10 min, zero risco.
modal dedicado com barra de progresso própria. Melhor visual, mas só vale depois do gate; o gate resolve o custo hoje.
2

Flag de onboarding escrito e nunca lido

CONFIRMADO — COM NUANCEuseDownloads.ts:113-115 · :130

Fato cravo (grep): scrcpy_onboarding_done aparece uma única vez — o setItem. Nenhuma linha lê o flag, e checkScrcpy abre o modal sempre que !found.

Nuance que a v1 ignorava: reabrir o modal enquanto o binário não existe é comportamento razoável — o app não funciona sem scrcpy e o modal é o melhor guia. O erro real é ignorar a preferência de quem já completou o setup: se a instalação é perdida, o modal volta a cada boot, com o botão Continuar desabilitado, recursivamente.

Melhor fix: if (!res.found && !localStorage.getItem('scrcpy_onboarding_done')) setIsOnboardingOpen(true). Quem já completou recebe o status vermelho normal no header (com caminho manual via popover do Engine); quem fechou o modal sem completar continua sendo guiado — o flag só é escrito ao completar, então o loop não reaparece.
Esforço: ~10 min + teste unitário de checkScrcpy com invoke mockado.
apagar o flag morto e manter o comportamento atual — mais simples e honesto, mas preserva o loop irritante que motivou o achado.
3

<button> aninhado + chips inalcançáveis por teclado

REENQUADRADOSidebar.tsx:219-311

O que fica: o card é <button> contendo outro <button> real ("Ir para wireless", linha 298) — proibido pelo content model da tag; os chips de transporte são span role="button" sem tabIndex e sem onKeyDown, então nunca recebem foco; e role="button" externo não pode conter focáveis (regra ARIA).

O que a v1 exagerou: não há mau funcionamento observável no WebKitGTK — o stopPropagation do botão interno impede o duplo disparo, e o warning do React só aparece em dev. O custo real é validade de HTML e a11y (teclado e leitores de tela), não crash.

Melhor fix: card vira <div> com onClick (a seleção por mouse fica); chips e "Ir para wireless" viram <button> reais. HTML válido, chips entram no ciclo de Tab, nenhuma regra ARIA violada (o container externo não carrega role). Seleção por teclado entra pelos chips, que chamam o mesmo onSelectDevice.
Esforço: ~30-40 min. Sidebar.test.tsx já existe — estender com teclado nos chips.
manter <button> externo e só adicionar key handler nos chips — deixa o aninhamento inválido e a regra AARI quebrada.
4

Cores do terminal dependentes do idioma

CONFIRMADO — REGRA CORRIGIDALogPanel.tsx:18-24

Regra real do código: falha|erro|aviso|pronto|iniciad|concluíd (pt) e failed|error|connected|success|ready (en) têm semântica; ru, fr, id, zh-CN, zh-TW e ar ficam sem cor em quase tudo. Os marcadores estruturais ([ADB], [SYSTEM], [MIC]) cobrem só uma parte das linhas — o resto dos t('logs.*') é texto nu (ex.: logs.adbPrefix é '[ADB] {message}').

Melhor fix (estrutural): LogEntry ganha level?: 'info'|'warn'|'err'|'ok'; appendLogs aceita o nível; os ~10 emissores que conhecem o significado da linha passam o nível na chamada (useSession, useDevices, useDownloads). logColor respeita level primeiro, heurística de palavras como fallback. É i18n de verdade — nenhuma palavra para adivinhar.
Esforço: ~45-60 min. Locales não mudam; muda a assinatura de appendLogs e o render.
quick fix de regex: marcadores primeiro + manter as palavras pt/en como fallback. 20 min, resolve 90% do dia a dia, mantém a heurística binária para os outros 6 locales.

5

Trocar de aba com sessão ativa não avisa

CONFIRMADOControlPanel.tsx:260-269 · App.tsx

O backend substitui a sessão registrada (comportamento correto); a lacuna é de visibilidade — nada na UI guarda qual modo está rodando, então Iniciar na aba nova mata a sessão antiga sem aviso.

Melhor fix (sem backend): guardar o modo no handleStart (startedModeRef.current = config.sessionMode); num próximo start com isRunning e modo diferente, interpor um showAlert de confirmação antes de runScrcpy. Uma vez por troca, não um aviso permanente.
Esforço: ~30 min incl. chave de i18n ×8.
emissor do modo no scrcpy-status (registry guarda o modo) — nova fiação no backend, desnecessária para o caso.
6

any nos handlers de config

CONFIRMADO — FIX É O GENÉRICOSelect.tsx:9-25 · ControlPanel.tsx:209 · SessionBehavior.tsx:98

Cravo: onChange: (val: any) no Select contamina tudo acima dele. O risco concreto: um campo recebendo o tipo errado (ex. micBitrate como string) cruza para o backend sem erro de build e só quebra em runtime.

Melhor fix: Select<V extends string | number = string> com options: { value: V }[] e onChange: (value: V) => void — a inferência automática cobre os ~30 usos sem mudar nenhum call site na maioria — mais handleChange<K extends keyof ScrcpyConfig>(field: K, value: ScrcpyConfig[K]). Botar tipo errado num campo vira erro de compilação no ponto exato.
Esforço: ~45-60 min, mecânico (o compilador aponta cada call site que quebra). Pega regressão de campo para sempre.
7

showAlert com 10 parâmetros posicionais

CONFIRMADOApp.tsx:100-125

13 call sites; pelo menos um passa undefined de marcador de posição para encostar num argumento posterior — ordem por memória é onde esse padrão vira bug de verdade.

Melhor fix: assinatura showAlert(opts: AlertOptions) com { title, message, kind?, actions: AlertAction[] }; atualizar os 13 call sites (o compilador aponta um a um). ThemedModal não muda.
Esforço: ~30 min. Qualquer erro de migração = erro de TS, não de runtime.
8

Re-renders 4×/s do mic-level atravessam a árvore

CONFIRMADO — FIX MUDOU DE DIREÇÃOApp.tsx:365-388 · Sidebar/ControlPanel sem memo

Confirmado: com a ponte de mic ativa, mic-level chega ~4×/s e cada evento re-renderiza o App inteiro. O que mudou: o fix da v1 (memo(Sidebar)) não funciona — os callbacks passados ao Sidebar são recriados a cada render, então a comparação de props nunca empata; consertar isso exige useCallback em toda a cadeia, frágil a cada handler futuro.

Melhor fix: isolar o medidor — componente <MicMeter> dentro do ControlPanel que assina mic-level/mic-route, guarda os valores em estado próprio e reseta via prop sessionRunning (muda só quando sessão liga/desliga). O App deixa de ouvir esses eventos e para de renderizar 4×/s; nada de memo em cadeia.
Esforço: ~30-40 min. Componente testável com mock de listen.
memo + useCallback em toda a cadeia — mais código, frágil a novos handlers, mesmo resultado.
